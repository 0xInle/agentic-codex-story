# Светлая система слайдов для презентации об агентной разработке

## Цель

Переработать все 14 сцен интерактивной презентации в единую светлую корпоративную систему ВебЗайма. Каждый слайд должен быть понятен слушателю без чтения технического кода, удерживать внимание одной главной мыслью и давать наглядный визуальный пример того, что докладчик раскрывает устно.

## Утверждённый формат сцены

Каждая сцена сохраняет существующие маршруты, номер и выезжающий блок `Текст доклада`, но её экранная поверхность меняется на одинаковую композицию:

1. Светлый лазурно-белый фон, фирменный знак ВебЗайма слева и номер сцены справа.
2. Один верхний заголовок, подобранный так, чтобы он помещался на одной строке desktop-экрана.
3. Две равные смысловые области ниже заголовка:
   - слева — одна короткая ключевая мысль без повторения заголовка;
   - справа — визуальное доказательство: схема, структура папок, стилизованный Markdown-документ, маршрут работы или диаграмма ролей.
4. Hover/focus-подсказки остаются поверх элемента и коротко объясняют его. Они не должны сдвигать компоновку.
5. Полный сценарий рассказа остаётся только в выезжающем `Тексте доклада`; на слайде не показывается длинный конспект.

`ФИЧА / 01` и дублирующий `h2` удаляются со всех сцен.

## Язык

Экранный текст и подсказки используют понятные русские термины. Английское название сохраняется лишь там, где оно помогает применить практику в коде, и сразу расшифровывается в скобках:

- `scope` — «границы задачи»;
- `runtime` — «работающее приложение»;
- `reviewer` — «агент-проверяющий»;
- `legacy` — «старый код»;
- `SPEC.md` и `AGENTS.md` — названия файлов, рядом с которыми есть русское назначение.

## Визуальный словарь

Фирменный знак используется компактно, без плашки и без имитации логотипа текстом. Фирменный элемент из раздела 4 брендбука — плавная синяя линия — появляется как ненавязчивая декоративная траектория на светлом фоне. Цветовая иерархия: графитовый текст, синий для структуры, Pacific Blue для вторичных связей, aquamarine для активных/подтверждённых элементов.

Схемы рисуются средствами интерфейса, а не подгружаются из сети. Разрешённые виды наглядных артефактов:

- дерево папок в стиле проводника редактора кода;
- карточка Markdown-файла с коротким фрагментом `SPEC.md` или `AGENTS.md`;
- линейный маршрут с подписанными этапами;
- диаграмма ролей с направлением передачи результата;
- доска доказательств: тест, сборка, браузер, скриншот;
- концентрические границы прав доступа;
- цикл улучшения следующей фичи.

## Визуальные доказательства по сценам

| № | Главная мысль слева | Визуальная часть справа |
|---:|---|---|
| 1 | Агент собрал сайт за короткие запросы, но результат стал фичей только после проверки. | Маршрут «идея → контекст → реализация → проверка» как цепочка карточек. |
| 2 | Человек определяет направление; агент экономит время на повторяемом. | Три уровня: решение человека, правило команды, изменение файлов. |
| 3 | Поиск хорошего примера каждый раз — скрытая потеря времени. | Замкнутый цикл «поиск → реализация → проверка», разрываемый сохранённым примером. |
| 4 | Короткое правило рядом с кодом помогает следующей фиче. | Маршрут «вопрос → правило → следующая задача» и компактная карточка Markdown. |
| 5 | Первая задача должна быть понятной, обратимой и проверяемой. | Разделение безопасной зоны, разрешённых файлов и старого кода. |
| 6 | Контекст показывает нужное место в проекте, а не весь репозиторий. | Дерево папок в стиле VS Code с подсвеченными `docs`, `src`, `tests`. |
| 7 | Агенту нужны эталон, контракт и граница старого кода. | Три подсвеченные карточки и приглушённая зона «старый код». |
| 8 | SPEC описывает ожидаемый результат, контекст — место и правила работы. | Две Markdown-карточки: `SPEC.md` и `AGENTS.md` с короткими пунктами. |
| 9 | Хорошая фича проходит видимую цепочку, а не один «магический» запрос. | Маршрут «задача → план → реализация → проверка → показ». |
| 10 | Отчёт агента не заменяет фактический результат. | Доска с подтверждёнными тестом, сборкой, браузером и скриншотом. |
| 11 | Субагенты полезны, когда у каждого отдельная роль и граница. | Схема «исследователь → исполнитель → агент-проверяющий». |
| 12 | Независимая проверка сравнивает код с задачей и фактами. | Три входа `SPEC.md`, изменения, доказательства → вердикт. |
| 13 | Инструменты дают только те действия, которые нужны на этом шаге. | Слои доступа: код → браузер/логи → ограниченное действие → подтверждение. |
| 14 | Каждая проверенная фича пополняет общий опыт команды. | Цикл «боль → контекст → фича → доказательство → новое правило». |

## Границы реализации

- Сохраняются 14 сцен, маршрутизация, клавиатурная навигация, fullscreen, доступные hover/focus-подсказки и выезжающий текст доклада.
- Не добавляются удалённые изображения, API, backend, аналитика, TypeScript или реальные вызовы Codex/MCP.
- Контент продолжает принадлежать `src/content`; текст доклада не переносится в JSX.
- Слайды должны оставаться читабельными без вертикальной прокрутки в desktop-viewport; на мобильном допускается адаптивное вертикальное расположение.

## Проверка результата

Для реализации будут добавлены/обновлены тесты, подтверждающие: 14 сохранённых маршрутов, новые короткие заголовки, отсутствие повторного экранного заголовка и `ФИЧА / NN`, наличие смыслового тезиса и визуализации у каждой сцены, русские пояснения ключевых терминов, работоспособность drawer/клавиатуры/hover. Затем будут запущены content validation, focused unit/component tests, `npm run verify`, Chromium E2E и browser screenshots в desktop-разрешении.
