# Инструкции репозитория Agentic Codex Story

## Обзор проекта

Этот репозиторий содержит локальное интерактивное образовательное приложение,
описанное в `SPEC.md`. `SPEC.md` — источник истины для результата продукта,
`IMPLEMENTATION_PLAN.md` задаёт порядок выполнения и файловый scope, а
`docs/implementation-progress.md` хранит статусы задач и evidence.

При противоречии инструкций соблюдайте такой порядок:

1. Текущий явный запрос пользователя.
2. `SPEC.md` для утверждённого scope и дизайна продукта.
3. `IMPLEMENTATION_PLAN.md` для порядка задач, зависимостей, файлов, контрактов и проверок.
4. Этот `AGENTS.md` для операционных правил репозитория.
5. `START_HERE.md` для цикла выполнения.

Не меняйте утверждённые дизайн или scope молча. Остановитесь и запросите review,
если необходимое изменение противоречит этим артефактам.

## Утверждённые технические ограничения

- Только JavaScript. Используйте `.js` и `.jsx`; не добавляйте TypeScript, `.ts` или `.tsx`.
- Используйте утверждённый frontend-стек React + Vite, когда активная задача доходит до настройки приложения.
- В проекте нет backend, аутентификации, server-side persistence, CMS, аналитики или сбора пользовательских данных.
- Не выполняйте реальные вызовы Codex, MCP или внешних runtime API. Поведение Codex, MCP, терминала и оркестрации, показанное приложением, должно быть локальной симуляцией.
- Не добавляйте секреты, обязательный `.env`, production-доступ, динамическое выполнение кода, `eval`, выполнение пользовательских shell-команд или небезопасный HTML.
- Основное поведение презентации не должно зависеть от сетевого соединения во время работы.
- Не устанавливайте зависимости, если активная задача явно не указывает установку зависимостей в своих шагах и файловом scope.

## Владение репозиторием и контентом

- Контент продукта должен находиться в `src/content` и его специализированных подпапках.
- React-компоненты отображают структурированный контент; они не должны становиться альтернативным хранилищем контента.
- Заметки докладчика не должны находиться в JSX. Храните их в `src/content/speaker-notes`.
- Глобальная навигация и состояние презентации принадлежат специализированным state/presentation-модулям из плана, а не визуальным компонентам.
- Детерминированная симуляция должна быть управляемой данными, воспроизводимой, сбрасываемой и не содержать случайных таймингов или реальных внешних вызовов.
- Сохраняйте узкую ответственность файлов. Не вводите гигантский универсальный компонент или несвязанный рефакторинг.

## Правила выполнения задач

- Выполняйте только одну implementation-задачу в один момент времени. Задачи в текущей утверждённой фазе выполняются строго последовательно, без дополнительного подтверждения человека между успешно завершёнными задачами.
- Полностью прочитайте активную задачу до редактирования.
- Убедитесь, что выполнены все зависимости и phase gate, названные активной задачей.
- Изменяйте только файлы, перечисленные в активной задаче. Если требуется другой файл, остановитесь и запросите обновление плана до редактирования.
- Не начинайте позднюю задачу, смежную уборку, попутный рефакторинг или исследовательскую фазу в том же проходе.
- Запускайте все task-specific проверки в точности так, как они перечислены активной задачей.
- Обновляйте evidence в `docs/implementation-progress.md`: файлы, команды, результаты, ограничения и состояние коммита.
- После каждой задачи записывайте фактическое evidence и отмечайте её `completed` только после успешного прохождения всех task-specific проверок. Затем автоматически начинайте следующую незавершённую задачу той же активной фазы.
- После phase gate остановитесь и запросите human review до начала следующей фазы. Никогда не переходите фазовую границу автоматически.
- Немедленно остановитесь, если задача blocked; обязательная проверка не выполняется; исправление требует файл вне разрешённого scope; нужно изменить `SPEC.md`, scope или ключевой архитектурный контракт; либо документы репозитория противоречат друг другу.
- Не делайте commit, если директория не является инициализированным Git-репозиторием. Если Git существует, делайте commit только когда его разрешает активная задача или пользователь.

## Правила тестирования и верификации

- Используйте TDD для детерминированного поведения: напишите падающий тест, наблюдайте ожидаемое падение, реализуйте минимальное поведение и повторно запустите focused test.
- Выбирайте тесты по поведению и риску: чистая логика использует unit-тесты; UI-поведение — component/integration-тесты; критичные пользовательские пути — Playwright; layout — browser verification; клавиатура и фокус — accessibility-проверки; разрешения и зависимости — security review.
- Никогда не ослабляйте тест или валидатор только ради прохождения проверки.
- Считайте вывод команд, наблюдения браузера и проверенные артефакты evidence. Утверждение об успехе без свежего evidence недействительно.
- `npm run verify` — финальный технический gate после того, как Task 4 создаст необходимые package scripts. Он не заменяет task-specific проверки или human review.
- Результаты dependency audit требуют человеческой интерпретации и не считаются автоматически pass/fail.

## Запрещённые изменения

- Никакого backend, реальных вызовов Codex, реальных вызовов MCP, интеграции внешних runtime API, production deployment или выполнения кода, предоставленного пользователем.
- Никакой миграции на TypeScript, Redux, звука, аналитики, больших видео, ненужных 3D-библиотек или неутверждённой опциональной зависимости.
- Никаких заметок докладчика в JSX и никакого хардкода контента продукта вне `src/content`.
- Никаких недетерминированных таймингов симуляции, неконтролируемых animation loop или заявлений, что симулированный вывод является реальным.
- Никаких правок вне точного file list активной задачи.
- Никакого молчаливого изменения scope, пропуска верификации, сфабрикованного evidence или автоматического перехода к следующей задаче.

## Протокол завершения

Перед тем как сообщить о завершении задачи:

1. Повторно прочитайте её цель, зависимости, file list, контракты, проверки и ожидаемый результат.
2. Убедитесь, что изменены только разрешённые файлы.
3. Запустите каждую task-specific проверку и прочитайте полный результат.
4. Запишите evidence о прогрессе и все ограничения.
5. Отметьте только активную задачу как `completed`, когда её проверки пройдены.
6. Если в активной фазе есть следующая незавершённая задача, последовательно продолжите с ней. Иначе запустите phase gate, запишите его evidence и остановитесь для human review.
